# Аудит Flowix

Дата: 3 ноября 2026. Осмотр исходников и локальные проверки; production и содержимое базы не исследованы.

## Оценка

Есть полезный прототип и собственный интерфейс. Базовая технология выбрана нормально: TypeScript, браузерное расширение, Next.js, PostgreSQL/Supabase. Причина переработки — разрозненные модели данных, хрупкая запись и отсутствие законченного командного сценария. Более сильная языковая модель сама по себе не делает переписывание необходимым.

Новая реализация оправдана в ограниченном объёме: заново спроектировать запись, данные, воспроизведение и доступ; сохранить удачные пользовательские решения и визуальные материалы. Полная перерисовка всех экранов до работающего сценария не является первым этапом.

## Существенные находки

### 1. Запись не закреплена за выбранной вкладкой — высокий приоритет

В `flowix-mvp/apps/extension/src/background.ts:48` отправитель сообщения назван `_sender` и не проверяется. Захват заново выбирает текущую активную вкладку (`:197`), а обработчик переключения вкладок ставит трекер на новый активный таб. Контекст клика может относиться к одной странице, а снимок — к другой.

В новой версии сессия закреплена за `tabId`, `windowId`, origin. Источник события сверяется с фактическим Chrome sender. После асинхронного снимка повторно сверяются вкладка, документ и состояние viewport. При изменении результат отбрасывается с видимой ошибкой, а не молча прикрепляется к шагу.

### 2. Возможны гонки и неправильный порядок шагов — высокий приоритет

В том же файле состояние читается до сетевых запросов, новый flow создаётся при отсутствии `currentFlowId`, а `stepIndex` увеличивается после upload (`:178–275`). Два захвата могут увидеть одинаковые значения и создать разные flow либо одинаковые индексы. Ограничитель в 600 мс уменьшает частоту, но не сериализует медленные запросы. Локальный устойчивый журнал отсутствует.

Новая модель: стабильные идентификаторы, атомарное резервирование, сохранение локально до сети, очередь только для уже полученных изображений, идемпотентный серверный append. Браузерный адаптер и реальная очередь ещё предстоят.

### 3. Клиентские cookies используются как признак входа — высокий приоритет

`apps/web/src/middleware.ts` пропускает посетителя по `flowix-auth=1` либо наличию cookie с похожим именем. `auth-session-sync.tsx` записывает access token дополнительным JavaScript-cookie; `/api/auth/token` имеет fallback, возвращающий его без собственной проверки.

Это слабая защита маршрута и дублирование сессии. **Это не подтверждённый обход доступа к данным:** `lib/auth-server.ts` вызывает `getUser(token)`, API проверяет владельца, web-страница дополнительно получает пользователя. Правильность действующих RLS-политик в базе неизвестна. Новая версия разделяет проверенную личность, актуальное членство в workspace и разрешение операции; cookie-флаг не считается авторизацией.

### 4. Share не предоставляет командный доступ — продуктовый блокер

`apps/web/src/app/flows/[id]/page.tsx:138` копирует `window.location.href`. Чтение flow на той же странице фильтрует `owner_id = user.id` (`:102–107`). Приглашение, членство и роли команды в просмотренном приложении не реализованы. Скопированная ссылка сама по себе не решает доступ коллеги.

### 5. Основной viewer — storyboard, не готовый кликабельный прототип

Страница flow выводит `FlowCard`, `clickPoint` и fullscreen preview. В `ui-kit/flow-card.tsx` отметка клика отображается через `ClickArea`; перехода на следующий экран она не вызывает. Документация прямо называет продукт storyboard. На просмотренном маршруте нет модели связей между экранами. Это вывод об этой версии репозитория, не о возможных локальных изменениях пользователя.

### 6. Теряется часть данных клика

Расширение отправляет `selector` и `elementRect`. `api/flows/[id]/steps/route.ts` принимает эти поля в схеме, но не записывает их при insert. Сохраняются только `click_x/y` и `viewport_w/h`. Размеры берутся из объекта tab; для правильного hotspot нужна система координат фактически снятого content viewport с учётом масштабирования. Из точки нельзя восстановить точные границы нажатой кнопки.

### 7. Загрузки и квоты требуют переработки — высокий приоритет перед пилотом

В `api/flows/[id]/steps/route.ts` тип файла определяется заявленным MIME; нет явного лимита байтов или декодирования изображения в обработчике. Это не означает, что хостинг не имеет собственного лимита. Квоты проверяются отдельным count перед insert, поэтому без транзакции конкурирующие запросы могут пройти вместе. Ошибка месячного count пропускается. При ошибке insert уже загруженный объект не удаляется. Фактические ограничения БД и Storage вне репозитория не проверены.

Нужны ограничение запроса до чтения тела, проверка/перекодирование изображения, атомарная квота, стабильный capture ID и очистка незавершённых объектов.

### 8. Защита и схема базы не воспроизводятся из `flowix-mvp`

В дереве этого репозитория нет SQL-миграций или сохранённых RLS-политик. Web делает прямой CRUD, сервер использует привилегированный ключ с ручными owner-фильтрами. Отсутствие миграций в Git не доказывает отсутствие RLS в живой базе. Оно мешает проверить и воспроизвести защиту. Также нужно проверить, не позволяет ли прямой клиентский insert обойти квоты API.

Положительная находка: серверный service key читается в модуле с `import "server-only"`; подтверждённой публикации этого ключа в исследованных файлах нет.

### 9. Ранний репозиторий и лендинг смешивают два корня маршрутов

В `flowix` есть одновременно `apps/web/app` и `apps/web/src/app`; часть API лежит во втором. В `flowix-landing` аналогично сосуществуют `app` и `src/app/viewer`. Next.js игнорирует `src/app`, если существует корневой `app`. Поэтому эти части не следует автоматически считать доступными маршрутами. [Документация Next.js](https://nextjs.org/docs/app/api-reference/file-conventions/src-folder).

### 10. Воспроизводимые проверки отсутствуют

В `flowix-mvp` не найдено тестов или CI. README помечает typecheck/test как TBD; `dev:web` использует Windows-специфичный `set ...&&`. Результаты локального запуска приведены в [VALIDATION.md](VALIDATION.md), включая ограничения среды. Не следует выдавать отсутствие подтверждения за установленную неработоспособность production.

### 11. Зависимости нельзя переносить без проверки

В исходном lockfile используется Zod 4.3.6. Проверка этой версии через npm audit выявила [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5): риск исчерпания памяти при обработке определённых больших входных коллекций. Наличие затронутой версии не доказывает доступность эксплуатации через конкретные endpoint Flowix. В новой основе закреплена исправленная версия 4.6.7. Полный аудит остальных production-зависимостей старого приложения не проводился.

## Что сохраняем

- Опыт настройки captureVisibleTab, manual capture, popup и основной сценарий записи.
- Разделение web/extension, TypeScript, приватное файловое хранилище и серверную проверку пользователя как направления.
- Существующие визуальные компоненты и графику после проверки удобства. Их перенос отдельный, не механическое копирование всех файлов.
- Линейный MVP. Canvas, ветвления, DOM-клонирование и автообновление чужих сайтов не требуются для первой проверки.

## Границы проверки

Не было доступа к рабочим секретам, настройкам Supabase, политикам реального bucket, журналам, данным клиентов или Chrome-профилю с расширением. Secret scan истории Git и penetration test не проводились. Нельзя сделать вывод «утечки нет вообще» или «продукт безопасен» по этому осмотру.

Официальные основания: [Chrome tabs](https://developer.chrome.com/docs/extensions/reference/api/tabs), [жизненный цикл MV3](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle), [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client). Прямое чтение changelog.md вернуло ошибку формата; проверена [страница breaking changes](https://supabase.com/changelog?types=breaking-change). Изменения существующего Supabase не выполнялись.
